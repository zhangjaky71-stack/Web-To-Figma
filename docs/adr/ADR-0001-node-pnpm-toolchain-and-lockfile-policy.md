# ADR-0001 — Node / pnpm Toolchain and Lockfile Policy

**Status:** ACCEPTED  
**Date:** 2026-08-22  
**Applies from:** NODE-01  
**Portable package format:** `.wtf`

## Context

Web-To-Figma is a multi-application TypeScript monorepo containing a browser extension, Figma plugin and shared packages. Reproducibility matters because capture and reconstruction behavior must remain deterministic across developer machines, CI and future release builds.

NODE-01 also encountered a repository-level GitHub Actions blocker in which hosted-runner jobs fail before the first workflow step. That external failure must not become a reason to weaken dependency reproducibility rules or hand-author an unverified lockfile.

## Decision

### Runtime

The repository runtime baseline is:

```text
Node.js 24 LTS
```

Repository declarations:

```text
.nvmrc = 24
engines.node = >=24 <25
```

### Package manager

The package manager is pinned exactly:

```text
pnpm 11.22.0
```

`package.json` must contain:

```json
{
  "packageManager": "pnpm@11.22.0"
}
```

`.npmrc` must retain:

```text
engine-strict=true
shared-workspace-lockfile=true
save-exact=true
```

### Build / quality toolchain

NODE-01 pins:

```text
Turborepo          2.10.11
TypeScript         6.0.3
ESLint             10.8.1
typescript-eslint  8.67.0
Prettier           3.9.6
Vitest             4.1.11
```

TypeScript 6.0.3 is intentionally selected instead of moving ahead of the supported `typescript-eslint` TypeScript compatibility range. A future TypeScript major/minor upgrade requires compatibility evidence and a dedicated dependency/toolchain change, not an incidental package update.

### Exact versions

Core NODE-01 tooling uses exact versions rather than `^` or `~` ranges.

This reduces the chance that two captures/builds performed from the same repository commit silently use different compiler, lint or test semantics.

## Lockfile policy

`pnpm-lock.yaml` is an authoritative generated artifact.

It must be:

- generated by the pinned pnpm version;
- committed to the repository;
- shared across the whole workspace;
- reviewed like source code when dependency changes occur.

It must **not** be manually invented, approximated from package metadata, or copied from an unrelated project merely to satisfy a CI check.

## Bootstrap rule

A repository without an initial `pnpm-lock.yaml` may temporarily use:

```bash
pnpm install --no-frozen-lockfile
```

only for the purpose of creating the first authoritative lockfile.

During that bootstrap state, CI must preserve the generated `pnpm-lock.yaml` as an artifact so it can be reviewed and committed.

This state is temporary and NODE-01 cannot be marked DONE while it remains active.

## Frozen rule

Once `pnpm-lock.yaml` is committed, CI must use:

```bash
pnpm install --frozen-lockfile
```

and the bootstrap `--no-frozen-lockfile` path must be removed.

Any mismatch between `package.json` workspace manifests and the committed lockfile must fail CI.

## Quality gate

The canonical repository quality command is:

```bash
pnpm check
```

It must cover:

```text
foundation validation
lint
typecheck
test
build
format check
```

CI may expose these as separate steps for observability, but they are one logical NODE-01 quality gate.

## Build boundary

Each executable workspace uses:

```text
tsconfig.json       → complete source + tests typecheck context
tsconfig.build.json → source-only emitted build
```

Tests must not be emitted into production `dist/` output merely because they are included in the typecheck project.

## Foundation validation

`scripts/validate-foundation.mjs` is intentionally dependency-free.

It validates critical repository contracts before dependency installation, including:

- workspace files;
- exact toolchain versions;
- Node/pnpm policy;
- build/typecheck script boundaries;
- shared-utils package export paths;
- `.wtf` extension and `application/x-wtf` MIME contract;
- CI bootstrap-vs-frozen lockfile state.

The validator supplements, but does not replace, pinned compiler/lint/test execution.

## GitHub Actions blocker rule

A hosted-runner/platform/account failure does not justify any of the following:

- marking NODE-01 DONE without the frozen-lockfile pipeline;
- hand-authoring `pnpm-lock.yaml`;
- lowering the toolchain quality gates;
- advancing canonical implementation status to NODE-02;
- merging NODE-01 solely because source review looks correct.

The current external blocker is tracked in GitHub Issue #5.

## Consequences

### Positive

- deterministic dependency resolution;
- explicit compiler/lint/test semantics;
- reproducible CI and local builds;
- clear upgrade ownership;
- no test files leaking into production build output;
- future nodes inherit a stable workspace contract.

### Cost

- toolchain upgrades require deliberate commits;
- initial lockfile creation requires an environment with registry access;
- NODE-01 remains blocked if no trusted environment can generate and verify the lockfile.

These costs are accepted because reproducibility is more important than bypassing a temporary CI/environment failure.
